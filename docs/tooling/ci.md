# Continuous integration

Every check runs before the code leaves the machine; GitHub checks once more what reaches `main` (ADR-0072), and runs the Rust tests on Linux after each merge into `develop`, blocking nothing (ADR-0088). A CI run per story would cost minutes of waiting for checks the pre-push hook already ran.

- **Work branches** (stories, features) are checked by the local Git hooks only ([Git workflow](./git-workflow.md#hooks-githooks)): a push that fails them does not leave the machine. No workflow checks them, and nobody waits for one.
- **`develop`**, after each pull request merged into it, runs the [`develop` CI](#the-develop-ci): the Rust checks and tests on Linux, then the [Rust caches](#the-rust-build-and-its-caches) saved for the review's pull request; no ruleset requires it and nothing waits for it, so a red run shows the same day a fault the Mac's checks cannot see, without stopping the run (ADR-0088, decision 4, EN-135).
- **A review**, the pull request from `develop` into `main` (ADR-0086), runs the CI below; the ruleset of `main` lets it merge only when every check is green. Nothing is checked again after the merge.

| Workflow | Job | When | Does |
| --- | --- | --- | --- |
| `ci.yml` | lanes | pull request into `main` | one job per lane of `check:all` ([commands](./commands.md#the-lanes-of-the-full-check)), in parallel, each its own check ([the lanes as jobs](#the-lanes-as-jobs)): restores the [Rust caches](#the-rust-build-and-its-caches), installs the npm packages (`npm ci`, whose `prepare` builds the release binaries; the Rust lane, which runs no npm package, `npm run rust:build` alone), then runs the lane's scripts in turn; each step a lane needs is chosen by a field of its matrix entry ([the steps of the lanes](#the-steps-of-the-lanes)): the Rust coverage lane installs `cargo-llvm-cov` on a missed key, the Rust lane and the test lane `cargo-deny`, and both fetch every crate of `Cargo.lock` for every target and the RustSec database, which cargo-deny reads offline; the docs lane runs `npm run build` last; the test lane keeps the JUnit test report, the lint lane the `git-hooks` binary |
| `ci.yml` | history | pull request into `main` | after the lanes, with the lint lane's `git-hooks` binary: the branch name (`git-hooks branch --name`) and the message of every commit of the pull request (`git-hooks commits`, [commit messages](./git-workflow.md#commit-messages)) |
| `ci.yml` | dependencies | pull request into `main` | GitHub's dependency review: a new vulnerable dependency fails |
| `codeql.yml` | analyze (`Analyze`) | pull request into `main`, push to `main`, weekly | CodeQL's security and quality queries on the TypeScript and on the workflows (`javascript-typescript, actions`), in turn in its one job, which keeps the check `Analyze` main's ruleset requires: a job per language would be named `Analyze (<language>)` (EN-134), a departure from GitHub's recommendation of one language per analysis (`REF-GH-CODEQL-TRIGGERS`) made to keep that one check; the Rust is not analysed, decided on 2026-10-18 to keep the blocking check short; the push keeps the analysis pull requests are compared with (`REF-GH-CODEQL-TRIGGERS`) |
| `site.yml` | site | push to `main` | builds and publishes the site and the playground on the [Rust caches](#the-rust-build-and-its-caches) `rust-caches.yml` saves under `main`, restored only; no release ([releases](./releases.md)) |
| `release.yml` | release | its button (`workflow_dispatch`), its only trigger | `release publish` refuses a branch other than `main`, computes the version from the last tag and the commits since, and makes the GitHub release on `main`'s head, its notes the bodies of the pull requests merged since that tag, the test report attached; no commit; nothing without a commit since that tag ([releases](./releases.md)) |
| `develop-ci.yml` | rust (`Rust tests and caches`) | push to `develop`, a person's merge; its dispatch by the features' auto-merge (`workflow_dispatch`) | the [`develop` CI](#the-develop-ci): restores the [Rust caches](#the-rust-build-and-its-caches), installs the cargo tools on a missed key and the npm packages, fetches every target's crates and the RustSec database, runs `check:rust`, then `rust:coverage` even after a failing check, and saves the caches under `develop`, a failing step included; required by no ruleset |
| `rust-caches.yml` | rust-caches | push to `main` | fetches every target's crates (`cargo fetch --locked`), compiles in release what `check:all` compiles, but the test lane's debug build of `backlog-index`, and saves `main`'s [Rust caches](#the-rust-build-and-its-caches); checks nothing |
| `links.yml` | links (`Link check`) | weekly and on demand | lychee checks every link of the Markdown files (ADR-0022), the outside ones rotting without a change of ours; exclusions in `.lycheeignore`, each with its reason (its run of 2026-10-15 failed on two links: the Kanban guide's HTTP 502, which answered again on 2026-10-19, and Adobe's live shapes tutorial's HTTP 403 to every client tried, excluded, EN-134); blocks nothing, required by no ruleset |
| `story-automerge.yml` | merge (`Story auto-merge`) | a pull request into a feature branch (`feature/**`), labelled, reopened or made ready | merges, always by a merge commit (ADR-0086), the owner's story pull request labelled `autonomous` into its feature branch; refuses any branch but a `US`, `EN`, `SP`, `CHK`, `AUD` or `VAL`; waits until the pull request reads `MERGED`, its auto-merge kept when not merged after its attempts |
| `feature-automerge.yml` | merge (`Feature auto-merge`) | a pull request into `develop`, labelled, reopened or made ready | merges, always by a merge commit, the owner's feature branch, `REV` or epic's refinement `SP` labelled `autonomous` into `develop` (the `SP` decided by the Product Owner on 2026-10-25, REV-009); refuses any other branch, a story straight into `develop` included; waits until the pull request reads `MERGED`, then dispatches the [`develop` CI](#the-develop-ci), a refused dispatch leaving a warning and the run green |

- **One workflow per purpose, its trigger its only condition** (ADR-0088): each file says its purpose in its name and its first comment, and no job nor step chooses itself by an `if:` reading the event or a branch (`github.event_name`, `github.ref`, `github.ref_name`, `github.ref_type`, `github.base_ref`, `github.head_ref`, and a ref or branch of the event's payload, such as `github.event.ref`, `github.event.pull_request.head.ref` or `github.event.workflow_run.head_branch`, by either syntax, `github['ref']` too, and in any case, `REF-GH-CONTEXTS`, `REF-GH-EXPRESSIONS`); a step chosen by its matrix lane or a cache missed, and a guard on a pull request's label, author or draft state, stay. `[F28.AC1]` (`tests/workflows.test.ts`) reads every workflow and names the file and the line of a condition that breaks it, with no exception since EN-134 split the auto-merge by its base: the stories' and the features' auto-merge are each chosen by their trigger's `branches`, `["feature/**"]` and `[develop]`, their job keeping only the guard on the label, the author and the draft state. Both start on `labeled`, `reopened` and `ready_for_review`, not `opened`: a pull request opened with its label sent `opened` and `labeled`, which started two runs, one merging and one skipped or finding it merged (#425 on 2026-10-19; research note 0026, §2), and one opened without the label waits for it; a draft opened with it is merged by its `ready_for_review` run, its `labeled` run skipped (`[F34.AC1]`, `tests/story-automerge.test.ts`). So the site, the release and the Rust caches, once three jobs of `release.yml` each under its own `if:`, are three workflows (EN-132); and `ci.yml` runs on a pull request into `main` alone, with no job under a condition (EN-133).
- **A required check is never left unrun by a filter**: GitHub reports a job skipped by its condition as a success, but a workflow filtered out by its branch or path filter stays "Pending" and blocks the merge (`REF-GH-REQUIRED-CHECKS`). Every job of `ci.yml` runs on every pull request into `main`, so each required check reports. `ci.yml` is not the only required workflow: `Analyze`, the job of `codeql.yml`, is the second, run on every pull request into `main` too ([repository settings](#repository-settings-done-once-by-the-owner)). Its `workflow_dispatch`, which timed the lanes on a branch (EN-111), went with EN-133, and with it the `if: github.event_name == 'pull_request'` that skipped `history` and `dependencies` on a run by hand; the lanes' times come from the review's run. A release branch's pull request runs every job (ADR-0079): the conditions that skipped release-please's branches went with it (EN-113).
- **Secrets** are checked three times: the secret scan (`tools/secret-scan`) on staged files at each commit, the same on every tracked file in `check:all`, and GitHub's secret scanning with push protection.
- **Code hygiene** beyond formatting is the lint's job — no `console`, `debugger`, `TODO`, unused code, nor rule disabled without its reason ([lint](../conventions/lint.md)) — not a check of its own.

## The lanes as jobs

`check:all` stays what the pre-push hook runs, its lanes at the same time on one machine. On GitHub's runner, the single job that ran it showed nothing until its end: its lanes took 139 s (`lint`), 265 s (`docs:build`), 326 s (`test`) and over 26 min (`check:rust`, compiled without a cache, not ended when the run was cancelled), run 39131147001 (EN-124, EN-125). So `ci.yml` runs each lane as a job of its own, the entries of one matrix (`REF-GH-JOB-PERMISSIONS`):

| Check | Lane's scripts, in turn |
| --- | --- |
| `Lint and types` | `lint` (oxlint with its type check, then the project's lint) |
| `TypeScript tests` | `test` |
| `Docs, playground and build` | `docs:build`, `playground:build`, then `build` |
| `Format, secrets and dependencies` | `format:check`, `lint:secrets`, `deps:audit`, `deps:unused`, `deps:outdated` |
| `Rust` | `check:rust` |
| `Rust coverage` | `rust:coverage` (EN-130) |

- **Each job its own check**, named by its matrix entry (`REF-GH-CONTEXTS`), with `fail-fast: false`: a lane failing leaves the others running to their end, each with its result on the pull request. Within a job, the first script failing ends it, as `check:all` ends a lane.
- **Every lane is run by exactly one job**: a lane's scripts start one job's, in their order, and no other job runs one of them; `[F24.AC1]` reads the matrix of `ci.yml` against the lanes of `tools/repo-tools/src/check_all.rs`, so a lane added there fails until it has its job.
- **The output as it comes**: a job runs its scripts itself rather than through `check:all`, which prints a lane's output only once it ends. The test job's Vitest reports each test file as it ends and annotates each failing test at its line on the pull request: the CI asks a JUnit report (`VITEST_JUNIT`), and `vite.config.ts` then sets the `default`, `github-actions` and `junit` reporters, a configured list replacing Vitest's own (`REF-VITEST-REPORTERS`, `[F24.AC2]`).
- **The history job waits for every lane**, whose lint lane passes it the `git-hooks` binary; a lane failing so skips it, the failing lane's check already blocking the merge.

## The steps of the lanes

Each step of a lane is needed by one of its scripts or the tests they run (ADR-0088, EN-133). A step every lane needs has no condition; the others are chosen by a field of the lane's matrix entry, a lane lacking the field leaving the step out, a nonexistent property being empty (`REF-GH-CONTEXTS`), never by a comparison of its scripts' names:

| Field | Lanes | Steps it chooses |
| --- | --- | --- |
| `node-packages` | every lane but `Rust` | `npm ci`, the npm packages, whose `prepare` builds the release binaries |
| `release-build` | `Rust` (`check:rust`: rustfmt, Clippy, cargo-deny, the check for Windows and `rust:fresh`, none an npm package) | `npm run rust:build`, the release binaries `rust:fresh` reads |
| `cargo-llvm-cov` | `Rust coverage` (`rust:coverage`) | `cargo install` of `cargo-llvm-cov`, on a missed tools key |
| `cargo-deny` | `Rust` (`rust:advisories`), `TypeScript tests` (`[F19.AC9]`'s advisories test, which runs `cargo metadata` and cargo-deny offline) | `cargo install` of `cargo-deny` on a missed tools key; `cargo fetch --locked`, every crate of `Cargo.lock` for every target, which `cargo metadata` reads offline (`REF-CARGO-FETCH`); `cargo deny fetch db`, the RustSec database |
| `git-hooks` | `Lint and types` | the upload of the `git-hooks` binary, which the history job runs |
| `test-report` | `TypeScript tests` | the upload of the JUnit test report, which the release attaches (ADR-0027) |

- **The release binaries are built once per lane, by `npm ci`**: its `prepare` runs `npm run rust:build`, and its log names every crate compiled. The step `npm run rust:build` that followed it, kept to name them, found them up to date. The Rust lane alone, which installs no npm package, runs that step instead (EN-130).
- **Every lane but the Rust lane installs the npm packages**: each runs a program npm installs, oxlint, Vitest, VitePress, oxfmt through the formatter (`tools/format`) or the installed packages' manifests (`dependencies unused`); the Rust coverage lane, whose script runs none, runs the formatter's tests under `cargo llvm-cov`, and they run the project's oxfmt (`tools/format/tests`). Since EN-130 the Rust lane's `check:rust` no longer runs the tests: none of its commands is a program npm installs.
- **One build passed as an artifact is not cheaper**: the lanes start together, and a build job before them would add its build to each lane's wait, while each lane's build already runs beside the others'.
- `[F28.AC3]` (`tests/workflows.test.ts`) reads the matrix and the steps of `ci.yml` against the lanes' scripts expanded through `package.json` and the tests that start cargo: each step chosen by a field, the binaries built once per lane, `npm ci` only in the lanes running a program npm installs, each cargo tool, the RustSec database and every target's crates only in the lanes calling them.

## The tools of each job

A job finds only what its own steps install or receive: GitHub's runner brings `git`, `gh`, the shell, rustup with `cargo`, which installs the toolchain of `rust-toolchain.toml` at its first call, and a Node.js with its `npm`, not the project's version. A lane's tests needed `cargo-deny`, which only the Rust lane installed, and #370's CI failed with exit 101 (AUD-027). So each tool a step calls, by its own commands or by the npm scripts they run, expanded through `package.json`, is given by a step before it in the same job (EN-136):

| Tool, as a finding names it | Called by | Given by |
| --- | --- | --- |
| `cargo-llvm-cov` | `cargo llvm-cov` | `cargo install --locked cargo-llvm-cov@<version>`, on a missed tools key |
| `cargo-deny` | `cargo deny`, its database's fetch included | `cargo install --locked cargo-deny@<version>`, on a missed tools key |
| `cargo-<subcommand>` | any other `cargo <subcommand>` neither built into Cargo nor brought by a component `rust-toolchain.toml` pins, `rustfmt` for `cargo fmt`, `clippy` for `cargo clippy` (`REF-CARGO-COMMANDS`) | `cargo install … cargo-<subcommand>@<version>`; none yet |
| the RustSec database | `cargo deny`, offline, but its fetch | `cargo deny fetch db` |
| every target's crates | `cargo deny` but its fetch, and `cargo metadata`, offline (`REF-CARGO-FETCH`) | `cargo fetch --locked` |
| Node.js | `node`, `npx`, a program npm installs, the installed packages' manifests (`dependencies unused`), the formatter's tests run under `cargo llvm-cov --workspace`, but given `-- --list`, which runs none | `actions/setup-node`, by `.nvmrc`, and `npm ci` |
| `target/release/<name>` | a command starting with that path | `npm ci`, whose `prepare` builds every release binary, `npm run rust:build`, `cargo build --release … -p <name>`, or the artifact a job it waits for (`needs:`) uploads from that path, downloaded into its folder and made executable by `chmod +x`, an artifact keeping no file mode (`REF-GH-ARTIFACT-MODES`) |

What each job calls, and the steps that give it:

| Job | Calls | Given by |
| --- | --- | --- |
| `ci.yml`, the lanes | each lane's tools, by its scripts | the steps its matrix fields choose, before the loop that runs its scripts ([the steps of the lanes](#the-steps-of-the-lanes)) |
| `ci.yml`, history | `target/release/git-hooks` | the artifact `git-hooks`, uploaded by the lint lane from `target/release/git-hooks`, downloaded into `target/release` after `needs: lanes`, then `chmod +x` |
| `develop-ci.yml`, rust | `cargo-llvm-cov`, `cargo-deny`, the RustSec database, every target's crates, Node.js | each its step, before `check:rust` and `rust:coverage` |
| `rust-caches.yml` | `cargo-llvm-cov`, to compile the tests given `-- --list` | its `cargo install` |
| `site.yml` | Node.js, VitePress and Vite | `actions/setup-node` and `npm ci` |
| `release.yml` | `target/release/release` | `cargo build --release --locked -q -p release` |
| `ci.yml`'s dependency review, `codeql.yml`, `links.yml`, `story-automerge.yml`, `feature-automerge.yml` | none: actions, `gh` and the shell | nothing to install |

- **`npm` itself is the runner's**: a script npm runs that calls cargo alone, `npm run rust:build` in `rust-caches.yml` and in the Rust lane, needs neither the project's Node.js nor its packages.
- **No step added**: when EN-136 wrote the check, every job already gave each tool it calls. Each row was broken once on purpose, the check naming the job and the tool: `npm ci` removed from `site.yml`, the `chmod +x` or the `needs: lanes` from the history job, the upload's path changed, `cargo-llvm-cov`'s install from `rust-caches.yml`, the release tool's build from `release.yml`, the database's fetch from the `develop` CI.
- `[F30.AC2]` (`tests/workflows.test.ts`) reads every job with `[F28.AC3]`'s reading of the steps, the scripts expanded and the cargo calls of the tests; a job with a matrix is read once per lane, with the steps its fields choose and its scripts for the loop that runs them, `[F28.AC3]` checking that a lane has each step, `[F30.AC2]` that it comes before the call (AUD-032). A tool given only after the step that calls it is missing, and a job lacking one fails the test as `<file> <job>: <tool>`, a lane as `<file> lanes (<lane>): <tool>`.

## The develop CI

`develop-ci.yml` runs once after each pull request merged into `develop`, on `develop`'s head, and blocks nothing (ADR-0088, decisions 4 and 5, EN-135):

| Merge into `develop` by | Starts the `develop` CI by | Why |
| --- | --- | --- |
| a person (a pull request the auto-merge did not merge, AUD-032) | its `push` to `develop` | a push by a person starts the workflows of its event |
| the features' auto-merge | its `workflow_dispatch`, `gh workflow run develop-ci.yml --ref develop`, once the pull request reads `MERGED` | its push by the `GITHUB_TOKEN` starts no workflow, a dispatch always does (`REF-GH-TOKEN-TRIGGERS`, `REF-GH-CLI-WORKFLOW-RUN`); with `--auto`, `gh pr merge` only enables the auto-merge on a pull request not yet mergeable (`REF-GH-CLI-MERGE`), so each attempt reads its state (`REF-GH-CLI-PR-VIEW`), and a dispatch before the merge would test `develop` without it |

- **Its two triggers are its only conditions** (ADR-0088, decision 2): `push: branches: [develop]` and `workflow_dispatch`, no `if:` on the event or a branch. No run is started twice: the auto-merge's push starts nothing, and a person's merge is not the auto-merge's, which runs only on a pull request labelled `autonomous`. `workflow_run` is set aside: it would run `main`'s file on `main`'s commit and could not save `develop`'s caches (`REF-GH-WORKFLOW-DISPATCH`, `REF-GH-CACHE`, research note 0026, §1).
- **The auto-merge's dispatch**: `feature-automerge.yml` has `actions: write` beside the merge's permissions, the one the dispatch needs (`REF-GH-REST-WORKFLOW-DISPATCH`), and `story-automerge.yml`, which dispatches nothing, has not; each merge step tries five times, ten seconds apart, and reads the state after each try; merged into `develop`, it dispatches, into a feature branch, it does not; not merged after the five tries, it dispatches nothing and fails, naming the pull request. Into `develop`, it first disables the auto-merge its `--auto` enabled (`gh pr merge --disable-auto`, `REF-GH-CLI-MERGE`): GitHub's later merge would be the `GITHUB_TOKEN`'s, whose push starts no `develop` CI, so a person merges it, and that push starts it (AUD-032); into a feature branch the auto-merge is kept, no `develop` CI following that merge. A dispatch GitHub refuses, the merge done, prints a warning annotation naming the cause, `::warning::` echoed (`REF-GH-WORKFLOW-COMMANDS`), and the step passes: the merge is what the run is for, and a red run would hide which of the two failed (EN-136). Neither script reads its base: each workflow holds the steps of its own (EN-134). `[F30.AC1]` (`tests/story-automerge.test.ts`) runs each script with `gh` and `sleep` replaced by stubs.
- **What it runs**: the Rust and Rust coverage lanes of `ci.yml` in one job, so that one build serves both and is saved whole: `npm ci`, whose `prepare` builds the release binaries `rust:fresh` reads and which installs the oxfmt the formatter's tests run; every target's crates and the RustSec database, read offline by cargo-deny; `check:rust`; then `rust:coverage`, run even after a failing check unless the run is cancelled (`REF-GH-EXPRESSIONS`), so that its build is compiled and saved.
- **Its caches, saved even after a failing test, never half made**: restored by `actions/cache/restore` without `restore-keys`, a new key starting from an empty `target/`, and saved at the end by `actions/cache/save`, unless the run is cancelled, which could leave a build half made, or the key was hit, its cache already saved (`REF-GH-CACHE-SAVE`). `actions/cache` saves only after every step passed: a test failing on Linux would leave the review's CI cold. A saved cache never changes (`REF-GH-CACHE`), so each is saved only once whole: the tools when the install's outcome is `success`, else a binary missing under the full key would make every later run skip the install and fail; the build when the outcome of `check:rust` is `success`, which a step skipped after the failure of `npm ci`, a fetch or the install is not (`REF-GH-EXPRESSIONS`, `REF-GH-CONTEXTS`), else its `target/` would lack their compilations for the life of its `Cargo.lock` (AUD-032). A run writes `develop`'s scope, the one the review's pull request reads first (`REF-GH-CACHE`), on a key missed in both `develop`'s and `main`'s: the first run for a key saves it, a later one hits it and saves nothing, and a run whose exact key `main` already holds restores it from there and writes nothing under `develop`, the review's pull request then restoring `main`'s, the same key.
- **Neither a concurrency group nor `continue-on-error`**: a group cancels a pending run, or with `cancel-in-progress` the running one, whose caches then go unsaved; `continue-on-error` would turn a red check green (`[F30.AC1]`, `tests/ci-caches.test.ts`).
- **Its own workflow, not `rust-caches.yml`'s** (ADR-0088, decision 1, ADR-0090): `rust-caches.yml` runs on a push to `main`, where nothing is checked again after the review's CI (ADR-0072), and saves `main`'s caches for the site and the release, compiling only; the `develop` CI runs the tests, on `develop` only. Joined, one file would hold two purposes, its trigger choosing `main`'s runs as well, with a test run after each merge into `main`, or an `if:` on the branch that decision 2 forbids.
- **Never blocking**: no ruleset requires its check, and no workflow waits for it, none having a `workflow_run` trigger (`[F30.AC1]`, `tests/workflows.test.ts`). Its job, `Rust tests and caches`, is named as no required check: its run is on `develop`'s head, the review's head commit, and a job name shared across workflows makes a required check ambiguous (`REF-GH-PROTECTED-BRANCHES`). A red run shows on the review's pull request, not required.
- **From the first merge into `main` that brings it**: a dispatch runs only a workflow whose file is on the default branch (`REF-GH-WORKFLOW-DISPATCH`), so until then GitHub refuses the auto-merge's dispatch into `develop` after its merge is done: the merge kept, the auto-merge's run green with its warning (EN-136); `story:finish` reads the pull request's state, not that run. The review after that merge reads its first runs, and the review's CI then restores its caches with no `cargo install` (VAL-031).

## The Rust build and its caches

The checks, the hooks and the docs' generators are Rust binaries of the workspace ([agent tools](./agent-tools.md)), so a job without caches compiles the toolchain's crates, the cargo tools and every dependency from nothing (EN-111). Two caches of the official `actions/cache` (`REF-GH-CACHE`), the same keys and paths in `ci.yml`, `develop-ci.yml`, `rust-caches.yml`, `site.yml` and `release.yml`, held equal by `tests/ci-caches.test.ts`:

| Cache | Holds | Key |
| --- | --- | --- |
| `rust-tools-…` | the pinned toolchain of `rust-toolchain.toml`, with its components and its Windows target; `cargo-llvm-cov` and `cargo-deny` | the hash of `rust-toolchain.toml` and the two tools' versions (`CARGO_LLVM_COV_VERSION`, `CARGO_DENY_VERSION` in each workflow's `env`, the versions of [dependencies](./dependencies.md#rust-tools)) |
| `rust-build-…` | Cargo's registry (index, crates) and `target/`: the release binaries, Clippy's, the coverage's and the Windows check's builds | the hash of `rust-toolchain.toml` and `Cargo.lock` |

- **Saved on `develop` by the [`develop` CI](#the-develop-ci), on `main` by `rust-caches.yml`**, each under its branch's name: after each pull request merged into `develop`, and at each push to `main` (EN-125, AUD-030, EN-135). From EN-125 to EN-135, `rust-caches.yml` saved both on a push, and the auto-merge's merges into `develop`, pushed by its `GITHUB_TOKEN`, started none (`REF-GH-TOKEN-TRIGGERS`): eight merges into `develop` on 2026-10-18 saved nothing, and the next review's CI installed the cargo tools again, 2 min 47 s in the Rust lane (research note 0026, §1). A run on `main` restores only `main`'s caches (`REF-GH-CACHE`), so the site and the release find the toolchain, the cargo tools and the build the first push to `main` for their keys saved. From EN-132 to AUD-030, `main`'s build alone was saved, by `site.yml`, and the tools' cache by no workflow: the site, which installs no cargo tool, cannot save a cache whose key promises `cargo-llvm-cov` and `cargo-deny`. A push to `main` starts the site and `rust-caches.yml` together, so the site restores the caches of the push before; on a key missed, its toolchain is installed at the first cargo call and its binaries compiled, as in a cold run. A cache saved by a pull request's run belongs to its merge ref and is restored only by re-runs of that pull request; a pull request's run restores the caches of its head branch, of its base branch and of the default branch, its head branch's searched first, and never a sibling's (`REF-GH-CACHE`). A saved cache never changes: the first run for a key saves it, and a later run that hits it saves nothing (`REF-GH-CACHE`). So the review's pull request, from `develop` into `main`, restores the caches the first run of the `develop` CI saved for its keys, else those `main` holds, which a `develop` CI run whose exact key `main` already held never wrote under `develop` ([the develop CI](#the-develop-ci)); a security update of Dependabot, from its own branch, only `main`'s. The jobs of `ci.yml`, `site.yml` and `release.yml` restore them and never save (`actions/cache/restore`, `REF-GH-CACHE-RESTORE`): no pull request starts from the caches of the previous one. Before EN-125 only a push to `main` saved them, and none had happened since 0.2.0: every pull request into `main` ran cold.
- **`rust-caches.yml` compiles in release what `check:all` compiles, with the same commands and flags**, on `main`, but the debug build of `backlog-index`, which the test lane makes when `tests/backlog.test.ts` runs it by `cargo run`, after `cargo fetch --locked`, so that the registry it saves holds every target's crates, not the host's alone, which the build fetches (`REF-CARGO-FETCH`, EN-116): `npm run rust:build`, Clippy, the tests under `cargo llvm-cov` given `-- --list`, which compiles them and runs none, and the Windows check. It checks nothing (ADR-0072: nothing is re-checked after the merge); a step that fails only leaves the caches unsaved. Without `restore-keys` there, a new key starts from an empty `target/`, so a cache never carries the build of an older `Cargo.lock`; a pull request may start from an older key's by prefix, compiling only what changed.
- **What a pull request compiles again**: the workspace's own crates, whose checked-out sources are newer than the cached build, never a dependency while `Cargo.lock` and the toolchain are unchanged; the cargo tools are installed only when their key is missed, and each only by the lanes that call it: `cargo-llvm-cov` by the Rust coverage lane, `cargo-deny` by the Rust lane and the test lane, which `[F19.AC9]` runs with the advisory database both fetch (EN-126, EN-133, EN-130). `CARGO_INCREMENTAL=0`: the incremental state of the workspace's crates would grow the cache and never be reused.
- **Built once per lane**: each lane's job builds the release binaries in `npm ci`, whose `prepare` runs `npm run rust:build` and whose log names every crate compiled; its scripts then find them up to date (EN-133). The history job runs the lint lane's `git-hooks` binary, passed as an artifact and made executable again, an artifact keeping no file mode (`REF-GH-ARTIFACT-MODES`).
- **The Rust lane's time, cold and warm**. Cold, with no Rust cache in the repository, run 39131147001 (its first attempt, the single job before EN-124): the cargo tools installed in 2 min 50 s, `npm ci` in 2 min 13 s, its `prepare` building the release binaries; `check:rust`, started with the lanes at 13:26:21, had not ended when the run was cancelled at 13:52:28, 26 min 07 s later, in its coverage step. Warm: measured at the run of the review's pull request, #370, that follows the first push to `develop` with EN-125, once the run of that push has saved the caches, and written here then; that push starts both at once, so the run it starts is still cold.
- **Kept 7 days unused, 10 GB per repository**, the least recently used removed first (`REF-GH-CACHE`): after 7 days without a run of the `develop` CI nor a push to `main`, the next pull request into `main` runs cold.
- **Never on demand**: `ci.yml` had a `workflow_dispatch` trigger to time the lanes on a branch (EN-111), which made two of its jobs skip themselves on such a run; it went with EN-133 (ADR-0088), the times now read at the review's run.

## Repository settings (done once, by the owner)

All under the repository page → **Settings**.

1. **General → Pull Requests**: check **Allow merge commits**, the only method (stories into features, features and reviews into `develop`, `develop` into `main`, ADR-0086); uncheck _Allow rebase merging_ and _Allow squash merging_; check **Automatically delete head branches**, **Always suggest updating pull request branches** and **Allow auto-merge**. **Features → Pull requests**: _Collaborators only_ (ADR-0026), the one barrier to an outside pull request since `external-prs.yml`, which closed one and never ran in 200 pull requests, was removed (ADR-0094).
2. **Actions → General → Workflow permissions**: keep _Read repository contents and packages permissions_ (each workflow declares its own); **Allow GitHub Actions to create and approve pull requests**, checked for release-please, is no longer needed: no workflow opens a pull request since EN-112, and the Product Owner may uncheck it.
3. **Pages → Build and deployment → Source**: **GitHub Actions**.
4. **Advanced Security**: enable **Dependency graph**, **Dependabot alerts**, **Dependabot security updates**, **Secret Protection** with **Push protection**. Leave CodeQL's _Default setup_ **off**: `codeql.yml` is the advanced setup, and both would conflict.
5. **Default branch**: `main` (the release, CodeQL's baseline, the caches, the public page).
6. **Rules → Rulesets** (ADR-0072):

   | Ruleset | Target | Bypass | Rules |
   | --- | --- | --- | --- |
   | `main` | default branch | none | restrict deletions, block force pushes, require a pull request (0 approval — one cannot approve one's own; merge method **Merge** only), require status checks with _branches up to date_: `Lint and types`, `TypeScript tests`, `Docs, playground and build`, `Format, secrets and dependencies`, `Rust`, `Rust coverage`, `Commit messages and branch name`, `Dependency review`, `Analyze` |
   | `develop` | `refs/heads/develop` | none | restrict deletions, block force pushes; no pull request nor status check required (the agent's pushes, checked by the pre-push hook); the [`develop` CI](#the-develop-ci) required by no ruleset |
   | `feature branches` | `refs/heads/feature/*` | Repository admin (the main thread's own pushes: `develop` merged in, its docs and rows) | require a pull request (0 approval, merge method **Merge** only: each story a bubble on the feature's line, ADR-0086); no linear history, no status check required |

Dependabot opens **security** updates only; they target `main`, the one exception to "releases only" (ADR-0072), pass its full CI, and `develop` then catches up; the release leaves its body out of the notes, its change written in the next review's text ([releases](./releases.md)). Version updates are the agent's, after reading the release notes ([versions and security](./versions-and-security.md)).
